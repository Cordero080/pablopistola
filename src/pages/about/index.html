Informed by two decades as a visual artist across abstraction, design, and representational art, I treat software as a craft where aesthetics and performance are inseparable. How I Got Here

My path to software was paved through disciplines that rely on structure, perception, and rigorous practice:

  • Artist & Draftsman: I've spent most of my life as a visual artist. Drawing and painting, then moved into digital art, motion graphics, and light VFX work. My background informs my development process. I approach engineering the same way I approach a canvas: I start with a rough sketch to organize the chaos, follow an impression, and refine until the composition and tone work, in this case, until the system works.
  • Linguist: I worked as a Spanish interpreter from 2005 to 2024. It taught me to think about communication and clarity. In my UI work, I lean toward icons and visual cues over text-heavy interfaces. I use symbols to bypass language barriers, using words only where they provide the most critical clarity.

The discipline and structure required to excel in traditional training directly influenced my engineering workflow and my workflow in general. I model software the way I model traditional training—through structure, progression, and continuous growth and refinement.

What Pulls Me Toward AI

The throughline across my life is structure in service of something that isn't fully controllable — a composition finding its own balance, and a translation finding the sense underneath the words. AI is the first medium I've worked in where I can build the structure and then watch something emerge from it that I didn't script. Pneuma routes a query through 43 philosophical archetypes and forces genuine tension between them before it answers, and the friction is designed while the resolution stays open. Archetope gives Tarot archetypes crossed with Myers-Briggs types real memory and a shared world, then watches unscripted rivalries and alliances fall out of the pairing alone. What draws me to AI, as opposed to treating it as automation, is what happens when you give a system enough structure to think and then get out of its way.

AI Engineering Practice

I work with AI coding assistants the way a careful engineer should: I don't just run the AI and trust the output. I built infrastructure around it.

The reason is straightforward: AI assistants are fast and capable, but they make mistakes that are easy to miss if you're moving quickly. A hardcoded API key in a commit. A function that got corrupted during a large edit session. A pattern that's inconsistent with the rest of the codebase. These aren't hypothetical — they're things that happened and that my tooling caught.

The setup takes maybe ten minutes to explain but it changes the risk profile of working with AI significantly. The AI writes code. The infrastructure reviews it. I make the calls.

Security Audit: A scanner runs automatically in the background on every edit. Checks for exposed API keys, unsafe database queries, and hardcoded secrets. CRITICAL findings block the next step and require a fix before continuing — permanently, across all projects.
Code Review (/audit): A slash command that points at any file and returns a structured analysis: is this doing too much? Is this logic duplicated? Is there dead code nobody calls? Read-only — it reports, never modifies. This is what caught a template literal corruption that silently consumed 400 lines of code as a string — the kind of error grep and linters miss entirely.
Architecture Diagram: When any of 13 tracked architecture files change, a script parses their real import statements, builds a live call graph, and rewrites the architecture doc automatically. The diagram is derived from actual source — not hardcoded. Documentation that stays current without me thinking about it.
